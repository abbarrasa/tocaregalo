# Instructions for AI agents

These instructions apply to the entire repository. Read this file, [MEMORY.md](./MEMORY.md), [README.md](./README.md), and the relevant code and tests before proposing changes. Current user instructions take precedence. Treat memory as a dated handoff and verify it against the working tree.

## Plan before implementation

1. Inspect the current state using read-only operations. Identify the task, affected components, existing behavior, risks, and relevant tests.
2. Present a concrete plan describing the proposed files and changes, validation, and any unresolved decisions.
3. Wait for explicit user approval before implementing the plan, including writing documentation, changing dependencies, or applying migrations. Approval of a plan covers its stated scope; do not ask again for each routine step. Environment permission prompts may still be necessary.
4. Implement the approved plan. If a material scope change is needed, explain it and obtain approval for the revised plan before implementing that change.
5. Validate the result, review the diff, update the handoff, and report the outcome and final Git state. Do not describe planned or untested behavior as complete.

Read-only inspection and planning may proceed before approval. A request to continue is not approval of an implementation plan that has not yet been presented. Do not repeat an already approved plan when resuming the same task.

## Required Git workflow

- Before changing branches, run `git status --short --branch` and inspect the local branches. Preserve all pre-existing tracked and untracked changes.
- For each new implementation task, create and switch to an English branch named `feature/<short-description-in-kebab-case>` starting at the current commit of local `dev`, for example `git switch -c feature/session-authentication dev`.
- Use local `dev` as it stands; do not silently update it from a remote. Verify the source branch exists and the target name is available.
- Uncommitted changes may carry across only when the switch is safe. If the switch would overwrite or conflict with local work, stop and explain the exact conflicting files and branch state. Do not discard or temporarily hide work to proceed.
- Do not run `reset`, `restore`, `clean`, `stash`, `commit`, `amend`, `rebase`, `merge`, `force-push`, or `push` unless explicitly requested. This workflow does not authorize commits or pushes.
- At completion, run `git status` and report the branch, modified/untracked files, and any pre-existing changes. Do not stage files unless requested.
- [The PR workflow](./.github/workflows/create-pr.yml) can create a PR to `dev` after an eligible push. Its existence does not authorize an agent to push or to claim a PR was created locally.

The Worker exposes health, public registration/login, authenticated account reads/logout, email-verification and password-recovery routes, authenticated group creation/list/detail, invitation/member operations, event creation/list/detail, owner draw/close operations and private recipient reads. Public login checks a password before internal session issuance.

## Clean Code and SOLID

- Prefer clear English names, small cohesive functions, explicit inputs and outputs, and comments that explain constraints or decisions. Preserve existing public behavior during refactors.
- Keep pure validation and business rules in [the domain layer](./src/domain/). Do not make one repository import another repository just to reuse validation or shared data structures.
- Apply single responsibility: transport handles HTTP, application services coordinate use cases, domain functions express business rules, and repositories handle persistence. Introduce services as real use cases require them, not as empty scaffolding.
- Apply dependency inversion and interface segregation: depend on small structural contracts such as [PersistenceDatabase](./src/persistence/d1.ts), with dependencies supplied explicitly. Avoid global service locators and concrete infrastructure dependencies in domain logic.
- Extend behavior through composition and focused contracts. Keep implementations substitutable by honoring their documented return values, errors, atomicity, and authorization semantics.
- Use strict TypeScript and explicit null/error handling. Avoid `any`, unchecked casts, broad exception swallowing, speculative abstractions, and inheritance added merely to satisfy a pattern.
- Use the existing ESM style with explicit `.ts` imports and erasable TypeScript syntax. Node executes the test files directly; do not introduce constructs that require an unconfigured transpilation step.
- Keep browser code in [frontend](./frontend/), outside Worker type inputs. Vue SFCs use the Vite toolchain and a separate strict frontend check. Backend checks retain TypeScript 7; the frontend workspace resolves TypeScript 6 explicitly for Vue tooling. Install all workspaces through the root lockfile, not a separate frontend lockfile.
- Browser use-case clients depend on the shared [HTTP contract](./frontend/src/http-client.ts), with one in-memory CSRF proof per application instance. Keep group/authentication contracts separate. Encode IDs/cursors, validate response shapes, retain bounded pages, and fence late UI updates/errors when navigating or switching resources. A current 401 clears private UI; missing/inaccessible groups share a generic message. Never infer server permissions from visible controls or retry ambiguous creation automatically.
- Invitation UI must query/show recipient emails only in owner administration. Acceptance uses the stored account email enforced by the server, with an explicitly entered code in a POST body, never a URL or browser storage. Sending, accepting and confirmed revocation use shared CSRF; do not retry ambiguous mutations automatically. A 202 is provider acceptance, not inbox delivery. Invalidate older list reads when mutating and clear private detail if owner authorization is lost. Shared browser pagination belongs in [pagination.ts](./frontend/src/pagination.ts), not another use-case client.

- Browser member removal requires explicit confirmation, shared CSRF and owner-only controls protecting the owner. Invalidate old reads and refresh bounded member/invitation pages after mutations. Do not equate a 503 with rollback: removal may already have committed with redraw pending, or service configuration may have prevented it. Explain uncertainty, allow safe state reads and never automatically repeat an ambiguous DELETE. Member-list absence cannot certify redraw completion. Fence late mutation replies and serialize member/invitation mutations in the group view.

- Browser event lists preserve the server's newest-first creation-time/ID order and opaque cursor, retaining one bounded page. Event clients share HTTP/CSRF but remain separate from group clients. Only the owner sees creation controls; server authorization remains authoritative. Send only nullable `closureAtMs`, never IDs, creation time or actor overrides. Convert explicit local date/time to an instant, reject invalid dates/DST gaps and explain the earlier-occurrence choice for repeated hours. Server time decides future validity. Never infer effective closure from a scheduled date or close/draw in the browser; do not invent missing event model fields. Fence old reads when creating and do not automatically retry ambiguous POSTs.

- Browser draw/close controls depend on current server lifecycle state and owner metadata, never scheduled dates or an inferred member count. Require explicit confirmation, bodyless POST with shared CSRF, duplicate/navigation guards and no automatic mutation retry. Reconcile conflicts/ambiguous outcomes using owner/state reads; hide actions if reconciliation fails and remove all detail on current 404. A current 401 clears private UI. Fence late read/mutation replies; validate event-scoped pending/ready/closed responses and do not expose recipients or keys. Closed events have no actions; unchanged membership reuses its draw, and only the server performs draws/closure.

- Private recipient UI requires explicit reveal and a fresh event-scoped GET without CSRF or caller actor/giver/draw selection. Render only the returned display name as text; retain the minimal validated response only in component memory, never URLs/storage/logs. Hide/clear invalidates pending reads; lifecycle refresh and mutation start synchronously clear the result before removing the panel, and remount hidden. Navigation/unmount/session expiry clear it too. A 409 is pending/stale; a recipient 404 alone must not remove otherwise accessible event metadata because closed-snapshot nonparticipants also receive it. The owner has no extra access. Do not infer eligibility from lifecycle UI, silently reuse an old result or claim client clearing can recall already observed information.

## Scalability and persistence

- Design for a stateless Worker. Do not use process memory as durable storage or as a reliable lock across requests.
- Use parameterized SQL, database constraints, appropriate indexes, and transactional D1 batches for related writes. Keep authorization predicates in the same SQL operation as the protected mutation where possible.
- Preserve atomicity and idempotency under concurrent requests. Never overwrite an existing draw's assignments during a retry or treat every database error as a duplicate. Membership changes may create a new immutable draw version for an open event.
- Consider query count, result size, bound parameters, batch size, CPU, memory, and concurrency when extending a use case. Verify current Cloudflare limits before depending on them. Add pagination and bounded work when introducing collection APIs or background processing.
- The legacy draw save prepares `1 + 2N` statements and encrypts all assignments concurrently. Lifecycle publication uses `2 + 2N` statements in one atomic batch and encrypts at most 16 assignments concurrently. Full snapshots and statement arrays still grow with participant count; do not claim unlimited capacity. Product limits or splitting a draw require approval and must preserve complete-draw atomicity.
- Add forward migrations in [migrations](./migrations/); do not rewrite migrations that may already have been applied. Test upgrades with existing data, not only fresh databases.
- Distinguish SQLite tests, local D1/workerd integration, and remote D1 verification. Passing one does not establish all three.

## Domain and privacy invariants

- A draw includes every participant, including the owner, requires at least three distinct participants, gives each person one recipient, and forbids self-assignment. Preserve uniform sampling over valid permutations.
- Use Web Crypto for randomness and cryptography. Recipient envelopes use AES-GCM authenticated to the key ID, draw, and giver; the HMAC index is draw-scoped. Preserve those bindings and key rotation behavior.
- Keep encryption keys and SendGrid credentials in Worker secrets, never in D1, source code, test fixtures with real data, memory documents, or logs. Do not log clear-text assignments or authentication tokens.
- Account provisioning is not authentication or email verification. All acting account IDs must come from a verified session before exposing repository operations through HTTP.
- Public registration requires email, password, and name; surname and phone are optional. Login accepts email or international phone plus password. The user explicitly requires only a minimum of six Unicode characters for passwords: do not introduce a password-specific maximum, composition rules, trimming, normalization, or silent truncation.
- Password authentication does not prove email or phone ownership. Store only salted Argon2id hashes in the separate credential table; never expose hashes in account responses.
- Email verification is available through authenticated/CSRF-protected requests and token-based confirmation. Login remains allowed before verification. Only the stored account email may receive a challenge; never accept a recipient or account ID override from the browser. Tokens are single-use, hashed at rest, expiring, and replaced by reissue. Verification consumption and account marking must stay atomic. Phone verification remains pending.
- Password recovery accepts email or phone but sends only to the stored email of an account with a password credential, including unverified accounts. It does not provision legacy credentials, verify email, or log the user in. Recovery tokens have a separate hash domain, one current token/account and a 30-minute configurable lifetime. Consumption, password update and revocation of all sessions must remain atomic. Public login must condition session issuance on the credential it verified, so a concurrent reset cannot leave a session issued from an old password. Requests return generic 202 responses and use bounded `waitUntil` work, not a durable email queue; delivery failures must not reveal account existence.
- The current membership policy permits only the owner to invite/manage members and create events; the owner cannot be removed through the repository. Public membership addition requires explicit invitation acceptance; the old `addMember` operation remains trusted internal provisioning only.
- Group HTTP operations derive the actor from the session. Creation requires exact Origin and session CSRF, generates IDs/timestamps server-side, and adds owner membership atomically. Detail reads hide missing/inaccessible groups behind the same 404. Lists filter current membership in SQL and use ID-based keyset pagination (default 20, maximum 50 plus one lookahead row); cursors never grant access. Invitation and member-management HTTP operations are exposed within their scoped policies below.
- Invitations are owner-issued to a normalized email, expire after seven days, and replace any previous token for that group/email on reissue. Require session, exact Origin and CSRF for request and acceptance. Acceptance must match the current account email and consume the hashed, purpose-separated token in the same D1 batch as membership insertion. Tokens are single-use, including after membership removal, and never confer an unchecked account identity. Existing members are not duplicated. Invitation acceptance does not verify email or issue sessions. Keep current-owner validation in issuance and consumption SQL. Limit requests to five/group/email and thirty/owner per fifteen minutes; non-owners must not consume the group's recipient quota. SendGrid delivery is synchronous and simulated in tests, with conditional failed-send invalidation, not durable retries.
- Invitation administration is owner-only. Lists order by normalized email with keyset pages (default 20, maximum 50 plus one lookahead row) and expose only email, dates and pending/expired/accepted state, never token hashes or consumption markers. Revocation requires Origin/CSRF and deletes only an active unconsumed invitation for the target email. It is idempotent for absent, expired or consumed rows and never removes memberships. Keep ownership and mutation predicates in SQL within the authorization transaction. Acceptance/revocation/reissue serialize through D1; an issuance after completed revocation creates a usable new invitation. Lists show the current row per group/email, not a delivery log or invitation history.
- Event HTTP creation requires an owner session, exact Origin and session CSRF. Accept only the current minimal model: explicit `closureAtMs` set to null or a safe integer strictly after the server creation timestamp. Generate event ID/time server-side and take group ID from the route. Keep the owner predicate in the insertion SQL. Detail reads require current membership, with the same 404 for missing/inaccessible events; legacy unlinked events stay inaccessible. Creation/detail do not run draws, schedule closure, deliver email or establish additional event attributes/lifecycle rules.
- Event creation time comes from the server clock at creation and is immutable. Preserve historical values; the D1 trigger rejects changes to `created_at_ms`. There is no public update endpoint. Keep future event-edit operations from changing this field.
- Event participation is all current group members, including the owner. Open events need at least three members to draw or close. Additions invalidate open-event draws but do not automatically reroll: the owner may add several members before requesting one draw. Public removal marks open events for automatic recalculation; with fewer than three members, they remain pending. Closed events retain their snapshots regardless of later membership changes. Scheduled closure time is a due time, not proof of effective closure; the owner may close early.
- [EventLifecycleService](./src/application/event-lifecycle-service.ts) coordinates versioned draws and effective closure through [EventLifecycleRepository](./src/persistence/event-lifecycle-repository.ts). Group membership revisions advance in D1 insert/delete triggers; revision, ownership and open-state checks guard publication/closure SQL. A retry for an unchanged revision reuses the current draw. Changed membership creates a new immutable version, preserving encrypted history. Closing creates or reuses an up-to-date draw atomically. Closed state/snapshot fields are immutable in D1. Legacy snapshots are adopted only when complete and equal to the current membership; do not infer historical closure from their dates.
- `GET /api/events/:id/draw` exposes lifecycle metadata to current members, never recipients. `POST` on that path draws; `POST /api/events/:id/close` closes. Both mutations are owner-only with exact Origin/CSRF. Already closed, undersized and persistent membership-contention cases return 409. Missing keys fail with 503 when encryption is needed. Configure distinct 32-byte hex cipher/index Worker secrets and a stable key ID; retain historical keys securely for private decryption. Do not reuse key IDs for different key material.
- HTTP removal commits membership revocation and pending-redraw flags before encrypting replacements. Process at most 20 eligible events per request, with up to three publication attempts/event. Failure or additional work returns explicit 503 after effective removal; retrying the idempotent DELETE resumes durable flags without rerolling completed revisions. Fewer-than-three events stay pending. The scheduled handler also recovers pending work automatically once deployed. Internal low-level membership removal only marks work; callers must coordinate lifecycle processing if they require immediate redraws.
- [ScheduledEventService](./src/application/scheduled-event-service.ts) processes at most 20 due closes and 20 eligible redraws per invocation, through a focused store and internal lifecycle contract. The native Worker scheduled handler uses the server clock, not the trigger's supplied timestamp, and is configured once/minute in UTC. There is no new public processing endpoint or fabricated user session. Owner identity comes from current group data and remains checked in lifecycle mutation SQL. Automatic closure requires a non-null inclusive due time in the publication/close SQL; manual closure may still occur early. Fewer-than-three jobs remain pending and become eligible on later membership changes.
- [0011_scheduled_event_processing.sql](./migrations/0011_scheduled_event_processing.sql) maintains `event_processing_jobs` atomically with event/membership writes. It backfills linked open schedules and pending redraws, indexes kind/next-attempt/event, queues removals, resets existing jobs on membership changes without creating redraws for additions alone, and clears work after publication/closure. Job version plus current membership revision fence retry writes, including deletion/recreation of a job. Do not replace this with an in-memory lock, detach it from membership transactions, or let a stale error postpone completed/new work.
- Event-processing backoff is 1, 2, 4, 8, then 15 minutes indefinitely, measured from failure processing. The persisted retry stage saturates at five; it is not a total-attempt counter or an abandonment limit. This policy is separate from the six-attempt email policy. Per-job failures/conflicts persist backoff and do not block other candidates; a failure to persist work propagates as invocation failure. Scheduled logs contain aggregate counts only, never raw exceptions, secrets or assignments. A successful handler outcome does not prove every job succeeded; inspect failed/deferred counts and pending D1 work.
- [0012_draw_notifications.sql](./migrations/0012_draw_notifications.sql) enqueues one durable notice/event/participant in the same transaction as each new manual or automatic closure. No historical backfill or open-draw notices. Queue rows reference event, draw and snapshot participant, never copy email addresses or clear assignments. [DrawNotificationService](./src/application/draw-notification-service.ts) processes up to 20 due rows after scheduled event processing, claims each immediately before sending with a random fenced 120-second lease, and resolves the account's stored email with current membership/closed-draw checks immediately before delivery. Do not accept browser recipient overrides or include the assigned recipient, credentials or decryption links in the notice.
- Notifications use the existing SendGrid transport and six known failed-attempt limit with nominal delays 1, 2, 4, 8 and 16 minutes; actual execution also depends on Cron/backlog. A 202 means provider acceptance, not inbox delivery. Membership removal atomically cancels pending/sending notices; rejoining does not reactivate them, and accepted notices remain accepted. A removal after the last check cannot recall a message already in flight. Lease tokens fence accept/fail writes, even after reclamation or cancellation; a late acknowledgement may settle an expired lease if its token was not replaced. Lost acknowledgement propagates instead of counting a known accepted send as failed. Expired reservations can recover without counting an unknown interrupted outcome as a known failure. Exactly-once external delivery is not guaranteed: timeout, lost acknowledgement or lease overrun can produce duplicates. Never claim otherwise or silently discard an ambiguous outcome.
- Event lists are scoped to one group and current membership in the same SQL statement. Order by creation time descending, then ID descending for ties, supported by `(group_id, created_at_ms DESC, id DESC)`. Use keyset pagination (default 20, maximum 50 plus one lookahead row) with a versioned creation-time/ID cursor. Old ID-only event cursors are invalid and must restart pagination. Return 200 with an empty list for an authorized empty/exhausted page, and the same 404 for missing/inaccessible groups. Cursors never authorize access or require the referenced event to exist. Group lists keep their existing ID order/cursors. Pagination is not a snapshot across requests.
- `GET /api/events/:id/recipient` uses [RecipientService](./src/application/recipient-service.ts) and [RecipientsRepository](./src/persistence/recipients-repository.ts), never caller-provided draw/giver/recipient identities. Current members can read only their own assignment from the current valid draw, both while open and after closure. The owner has no privilege to read another assignment. Pending/stale open events return 409; missing/inaccessible/unlinked events and nonparticipants in a closed snapshot share 404. New group members cannot read a closed event's assignment unless they were participants in its snapshot. Removed members lose access; re-enrollment restores it when the snapshot still applies. Closed snapshots may name recipients who have since left the group.
- Select membership, current revision and the actor's own encrypted assignment in one SQL read. After decryption, recheck membership, participation and the exact current draw in the same query that resolves the recipient's snapshot participation and account name. A changed/ineligible version returns 409 and revoked membership returns 404; do not return a plaintext result from an earlier selection. Each successful read returns only drawId and recipient accountId/displayName, with no-store and no contact/credential/envelope fields. Display names are current account names, not historical snapshots. No CSRF is needed for this read; do not add writes, mail or CORS permission.
- Active read keys use the existing key ID/cipher secret; optional `DRAW_PREVIOUS_CIPHER_KEYS_JSON` is a Worker secret containing an array of `{id,cipherHex}` for retained AES-GCM keys. Reject malformed configuration, duplicate IDs (including active/historical overlap) and missing requested keys with generic 503. Import only the selected nonextractable decrypt-only cipher key; do not require historical HMAC keys for decryption. AES-GCM authentication/corruption errors remain generic 500, never fallback to another assignment/key. Historical key retention for other uses remains unchanged.
- An archived draw ID or a stale open-event snapshot must not bypass current-draw selection. The low-level draw methods do not authorize callers. Do not expose them directly as endpoints. `DrawRepository.findByEvent` is a historical/latest-by-time lookup, not the authoritative current lifecycle state. `findRecipientForAccount` is membership-scoped but does not check lifecycle currency; the public API uses the dedicated recipient repository instead.
- Removing membership revokes scoped reads but preserves encrypted draw snapshots. Legacy events with no group remain inaccessible through membership-scoped queries. Do not silently assign ownership to old data.
- Member lists require current membership, order by account ID with bounded keyset pagination (default 20, maximum 50 plus one lookahead), and expose only accountId, displayName, joinedAtMs and isOwner. Never include contact details or credentials. HTTP removal is owner-only with exact Origin and session CSRF, protects the owner (409), and is idempotent for absent members. In one D1 batch, cancel active unconsumed invitations to the target account's stored email and remove membership, with ownership predicates in each protected mutation. Cancellation also covers absent membership to serialize safely against acceptance. Preserve expired/consumed invitation records and encrypted draws. Later invitations may re-enroll a removed account; sessions and unrelated groups are unaffected. Use MembersRepository for public removal; the old GroupsRepository.removeMember is an internal low-level operation without invitation cancellation.
- Closure is inclusive at its timestamp; the target processing delay is at most 60 seconds. The once/minute schedule and local tests do not certify this target: backlog, retry delay, platform latency and CPU/memory limits still apply. Measure it in a published environment without browser traffic before claiming compliance. Delivery retries stop after six known failed attempts. Only closed-draw notices currently use durable email; invitation, verification and recovery sends retain their existing delivery policies.

## Validation and environment

Use Node 24 or later and the commands in [package.json](./package.json):

```sh
npm ci
npm run test:unit
npm run test:integration
npm run typecheck
git diff --check
```

`npm test` runs the complete suite. Use meaningful regression tests for changed behavior, security boundaries, rollback, and concurrency; a mechanical refactor can rely on the relevant existing suite. Do not add tests that only mirror implementation details.

- `npm run test:frontend` runs browser client/component tests with Vitest/jsdom. This is not visual or real-browser verification. `npm run build:frontend` builds static assets in `dist/frontend`; CI checks this build too. `npm run typecheck` includes Node, Worker and Vue checks.
- For local browser development use `npm run dev:api` and `npm run dev:frontend`, then `https://localhost:5173/`. The local HTTPS Vite proxy preserves Origin and the Worker command sets the matching allowed origin. Do not weaken Origin/CSRF/cookie rules for development. No production asset hosting is configured by these commands.
- Browser sessions/CSRF and account state remain in memory/HttpOnly cookies. Never add auth codes or credentials to URLs, browser storage, logs or demo fixtures with real data. Retain the public password and optional-field policies in UI validation; never transplant the prototype's password maximum, mandatory phone, SHA-256 credential storage, unchecked identities or automatic browser-side closure.

- Node and Worker types are checked separately by [tsconfig.json](./tsconfig.json) and [tsconfig.worker.json](./tsconfig.worker.json). Both must pass for shared source changes.
- Miniflare starts workerd and may need permissions unavailable in a restricted sandbox. Report environment failures accurately; do not skip failing tests and claim success.
- If Node is missing from the agent PATH, locate the user's existing installation rather than installing a second runtime. See the environment notes in [MEMORY.md](./MEMORY.md). Request tool escalation when required; do not bypass sandbox restrictions.
- `npm run db:migrate:local` applies migrations to persistent local development state. The integration tests use separate ephemeral databases. Apply migrations only within approved scope.
- [wrangler.jsonc](./wrangler.jsonc) contains a local placeholder D1 ID. Do not deploy or modify remote resources unless the approved task includes that work. Never claim a dry run deployed anything.
